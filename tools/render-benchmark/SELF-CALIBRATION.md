# 渲染兼容 WPS · 自我校准规则（AI 执行手册）

> 触发条件：用户放入新文档到 `tools/render-benchmark/docs/`，或说「跑渲染对比」「校准渲染」。
> 目标：自研 OO 渲染尽可能接近桌面 WPS。**标准答案永远以 WPS 导出为准。**

## 执行流程（有新文档时按序执行）

### Step 1 检查材料
- `docs/` 有新文档？（docx/xlsx）
- `golden/` 有同名 WPS 导出 PDF？
  - **没有 → 先提醒用户**：用桌面 WPS 打开该文档 → 另存为 PDF → 放入 `golden/`（同名）。**不催促自造答案**。
- 都齐 → 继续。

### Step 2 跑自研渲染
- 用项目渲染管线（office/oo 管线）处理该文档，产出结果放 `mine/`（同名 PDF 或 PNG 页图）。
- 渲染失败/特性不支持 → 直接记录为「已知不支持」，进报告，不要硬造结果。

### Step 3 跑对比
```
cd tools/render-benchmark && node compare.mjs 文档名
```
- 输出差异百分比 + 差异热力图（`reports/xxx.diff.png`）。
- 判读：<2% 优秀 / 2~5% 可用 / >5% 需修。

### Step 4 归因分析（看热力图定位差异区域）
按此优先级归类原因：
1. **字体度量**（行宽断字位置不同 → 连锁分页偏移）——最大头
2. **分页/分节规则**（避头尾/孤行/keep-with-next）
3. **表格引擎**（合并单元格/跨页表头/列宽）
4. **特性缺失**（文本框/环绕/公式/艺术字）——记录为已知差异，不强修
在报告里写明：哪一页、哪块区域、归哪类原因。

### Step 5 修渲染（用户确认后执行）
- **从差异百分比最大的文档类型开始**（业务频率 × 差异度）。
- 一次只改一条规则/一个分支，**禁止顺手大重构**。

### Step 6 回归验证（铁律，不可跳过）
- 修改后 **全基准集重跑** compare：
  - 目标文档差异 ↓ ✅
  - **任何其他文档差异 ↑ = 修 A 坏 B，撤销本次修改**，换个思路（加条件分支而不是改通用路径）。
- 全绿才提交。

### Step 7 记录
- 在 `reports/calibration-log.md` 追加一行：
  `YYYY-MM-DD | 文档名 | 修改内容 | 该文档差异 X%→Y% | 其他文档回归情况 | 结论`
- 该文件是「校准进度」的唯一真相源。

## 铁律（永远遵守）

1. **改渲染代码前跑一次基线、改完必跑全量回归**——修 A 坏 B 禁止合入。
2. **标准答案 = WPS 导出**，永远不用想象或猜测补答案。
3. **排版规则互相纠缠**：断行变 → 分页变 → 全文档变。任何「通用路径」的修改都默认高危。
4. **自研渲染的定位**：画布内轻量预览。**高保真需求引导 OnlyOffice/WPS 服务**，不用自研硬扛。
5. 渲染引擎的正确性 =「不修坏」，不是「修对」——几千份文档无退化才是标准。

## 架构决策记录（2026-11-01 对话结论）

- 桌面 WPS 与自研渲染**同格式不同引擎**：docx 只存内容+指令，每个字的像素位置由排版引擎实时算——字体度量/排版规则/兼容 quirk 是差距来源，自研有物理上限。
- 长期架构：**两层**——画布缩略图自研（快）+ 高保真预览 OnlyOffice/WPS（准）。
